# 十部分分析规范

按以下顺序写。背景、数学和方法的深度以读者能解释因果关系、跟完案例和判断证据为准。小标题保留十部分映射，内容用连贯段落组织，以正常引文说明依据，不附信息类别标签。

## 1. 研究问题、背景与价值

先用具体情境讲清：谁在什么输入、目标和约束下，遇到了什么失败。把应用需求与论文实际研究的技术问题分开，说明论文覆盖哪一部分。

补充读懂该问题必需的背景：任务定义、关键对象、论文提出时的通行流程，以及为何在当时值得解决。区分原文提出的动机、其他文献的证据与自己推断的潜在价值。价值落到成本、错误类型、可用场景、科学解释或能力边界，不写抽象的“提升性能”。同样区分已展示的收益与尚未验证的下游价值。

## 2. 之前解决到哪里，为什么仍有不足

按解决问题的机制整理代表性路线，仅比较目标方法最早公开前已有的工作，优先当时最近且最强的可比方法；同期独立工作单独注明，后续进展放在第 9、10 节。核实已有方法在什么设置下已经有效、剩余限制是什么，以及限制是否触及本论文声称解决的问题。不要仅复述目标论文对竞争方法的介绍。

确有帮助时用小表比较“路线 / 已解决部分 / 关键假设 / 失败条件 / 来源”。分清没人研究、研究过但效果受限、成本过高、评测不充分和问题被重新定义。方法适用范围不同，不等于前人方法失效。

## 3. 从已有知识重建可能的思考路径

将本节写成基于历史证据的可能思路，用自然的假设语气引入，不声称知道作者私下如何思考。历史知识截止日期在文首交代一次；本节的前提限于该日期前已有的背景、失败模式、经验观察与相关工作。

先在工作记录中只列允许使用的前提，再组织成短而连贯的研究论证：

1. 哪个已有现象与通常的假设发生冲突？给出历史来源。
2. 旧方法为什么在该条件下遇到瓶颈？哪些因果连接有证据，哪些只是推断？
3. 已知工具、其他领域的做法或经验观察，提供了什么可迁移的视角？说明迁移成立所需条件。
4. 当时有哪些合理候选方向？只在有依据时对比替代路线，不能为了显得聪明虚构作者放弃过的方案。
5. 由此可以提出什么可检验的候选假设？保留其尚未验证的状态，并解释它为什么值得一试。

**防止事后倒推**：不能从“需要论文中的模块 X”出发，也不能用目标论文的消融提升、首次观察到的现象或后来成功作为旧知识。推导可自然接近论文思想，但不能把技术细节写成唯一必然结论。历史证据不足时缩短重建，指出断点，不补成励志故事。

作者在访谈、博客或论文中明确说过的 inspiration 可直接叙述并引用出处；自述的存在不等于重建中的所有因果关系得到证明。后出的综述只能用于今天的解释，不能混进当时可用的前提。

## 4. 核心 intuition

用一小段，通常 2–4 句，回答：在什么条件下，旧机制卡在哪里；新方案改变了哪个关键关系；为什么预计因此受益；依赖什么条件。先给读者可复述的本质，再介绍术语。

少用模块名，不逐条复述论文贡献，不提前塞入完整算法。类比如果有用，立刻说明对应关系与类比失效的边界。

## 5. 具体方法：真实实例的完整 pipeline

优先采用论文示例、官方代码测试样本或公开数据中的真实实例，给出来源和可复查定位。使用来源中的合成案例或自行构造的教学案例时，在引入例子时说明一次，不把它写成真实世界数据。贯穿一个例子说明任务输入、预处理、关键计算与状态、最终输出及实际使用方式。学习方法要区分训练期与推理期，说明哪些参数被更新、哪些信息只在训练时可见。

在每个关键步骤解释输入是什么、为何需要该步、发生了什么变换、得到什么输出。只保留帮助理解的形状、维度、单位或伪代码。对于统计、理论或非预测论文，将 pipeline 对应为对象、假设、操作/证明和得到的结论，不硬套神经网络。

真实输入不意味着中间状态和输出也被实测。没有运行时只能引用原文/代码中已公开的输出，或用“以一个简化例子手算”等普通叙述引入推演；不可写“运行得到”。不存在可用真实案例时简要说明缺口，再用构造例子帮助理解，不能将它冒充真实案例。

代码与论文不一致时标出版本和差异，避免拼接成一个实际上不存在的实现。

## 6. 核心数学与零基础理论解释

先判断数学承担的作用：模型定义、优化目标、算法更新、复杂度分析，还是带假设的定理。公式存在不等于存在理论保证，实验论文也不必被包装成定理论文。

按依赖顺序解释最少但足够的前置知识，例如向量、概率、期望、导数或条件独立。每个概念先用本方法中的对象说明“它表示什么、为什么需要”，再引入符号。给出简短符号表，明确标量/向量/矩阵、维度和必要单位。

只展开决定方法成立的核心推导链：

1. 从目标和假设出发，解释为何写下这个表达式。
2. 对每个非显然的等号、不等号、近似或优化步骤说明依据及条件。
3. 引入一个可手算的小例子演示关键操作，让读者知道这些数值用于讲解，不冒充论文测量。
4. 回到算法：最终表达式对应哪一步计算，理论覆盖哪些情形，哪些部分仍靠经验有效。

引用公式时核对原文。补出的步骤和简化推导通过“把这一步展开”“为了看清这个关系，先考虑一个简化情形”等正常叙述衔接，说明适用假设，不把自己的推导归给作者。推不出的地方指出具体缺口。原文没有证明时不得声称已证明，更不能用“显然”跨过关键困难。

确实没有需要展开的核心数学时，在本节说明方法主要依赖何种机制与实验证据，并简述必要定义或目标后结束。不为满足章节而加入无关公式。

## 7. 实验如何验证问题与 claim

以论文要回答的几个关键问题为单位，采用 **问题 → 验证实验 → 答案**。在对应结论附近引用相关实验或图表：

- 问题：把 claim 改写成可被实验区分的问句。
- 验证实验：哪些数据/条件、对比或干预能回答它，控制了哪些变量；必要时说明是否等算力、等数据、等调参预算。
- 答案：实际证据支持到哪里，有何替代解释或尚未覆盖的条件。

不罗列所有指标；保留影响判断的数量级、关键差异和必要不确定性。消融可能同时改变容量、计算量和优化过程，提升本身不能唯一确定机制解释。区分作者解释与自己的评估，保留会改变结论的负结果，不能补造随机种子、显著性或实验。

## 8. Take-aways

用少量有条件、可复用的结论收束：读者应更新什么认识、什么时候可尝试该方法、什么时候应保留怀疑。区分可迁移的思想、论文特定设置中的发现与未解决问题。不复读摘要，也不在此引入未经支持的新 claim。

## 9. 最脆弱的假设、一周检验与反例

挑一个最支撑核心结论、却证据最弱或最容易被现实条件破坏的假设。写清它为何关键、目前证据为何不足、失效会伤及哪条 claim。明确原文承认的限制与自己识别的风险。

围绕这一个假设给出**最小机制检验**；不要默认复现整套大型训练。计划至少包含：

- 假设及预测：预先写明哪些观察支持、哪些观察削弱它。
- 数据/模型/代码来源与最少资源；用户预算未知时明确采用的低资源假设，不虚称拥有某 GPU。
- 一个有意义的基线和尽量只改变目标因素的干预；保持相关预算与评测一致，考虑必要的重复和随机性。
- 主要观测指标与决策规则；提出建议阈值时解释为何这样设定，不冒充论文结论。
- 一周安排：先打通基线与测量，再做干预，最后分析误差/反例；给出失败时停止条件和低资源替代。

计划是未执行的提议。若一周无法检验核心 claim，明确较小实验只能测试哪个代理问题，以及不能外推什么。

设计一个尽可能具体的反例：可构造输入、数据分布或环境，如何保持问题其他条件，预期失败现象，以及什么结果会使自己撤回反对。区分“在论文适用假设内否定 claim”和“改变假设揭示适用边界”；分布外失败并不自动推翻有条件的原结论。

## 10. 从限制与需求出发的 follow-up idea

目标是形成一个有机制差异、可证伪且有现实价值的研究候选。先找到当前仍存在的需求，再追溯限制来自哪项假设、信息缺口、目标定义或机制；避免从“还能加哪个模块”出发。

围绕问题的不同说法、关键机制及邻近领域检索，打开最接近的原始工作并记录检索日期与关键查询。把候选与最接近方案直接比较：研究问题、核心机制、所需假设、可区分的预测。不要以新名字、未出现的关键词或“未检索到”单独支持 novelty。

最终只充分展开一个最有依据的候选：

1. **需求与证据**：哪个真实场景需要突破，以及谁或什么证据表明现有能力不足。
2. **中心假设与机制**：改变什么关系或问题表述，为什么可能绕开限制，新的代价和假设是什么。
3. **相对已有工作的区别**：最接近工作做到了什么，候选额外提出的可检验内容是什么；明确后来研究是否已解决原论文的缺陷。
4. **决定性检验**：什么最小实验能同时比较新方案与最强替代解释，何种结果会否定价值或核心机制。
5. **新颖性状态**：分别写已核实重合、暂未发现直接对应的部分，以及未检索范围。遇到直接重合时修改候选或如实判为已有路线，不硬凑新颖。

仅扩大模型/数据、微调超参、替换 backbone、叠加通用模块或换数据集不满足用户对非增量研究的要求，除非形成有证据的新问题或机制。用研究提议的语气说明方案及其待验证环节；当前检索能降低重复风险，不能证明绝对原创。无法形成可信候选时保留明确的研究缺口和所缺证据，不交付伪新颖的承诺。
