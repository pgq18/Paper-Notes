# 阅读与分析规范

笔记的目的，是帮助读者读懂一篇新论文并掌握它的主要逻辑与 idea。按下面八部分组织，重点放在思路如何产生、方法如何工作，以及关键实验说明了什么。检查点用于帮助取舍，不逐项扩写成小节。篇幅遵循 SKILL.md 的写作要求。

## 1. 研究问题、背景与价值

用一个具体场景说明：谁在什么目标和约束下，遇到了什么困难；解决它会改善什么。区分应用需求与本文实际处理的技术问题。通常一至两段，只补读懂问题必需的背景，价值落到成本、错误类型、可用场景或能力边界。

此处把问题说具体，不提前罗列方法步骤。潜在价值用相应语气表述，不把尚未展示的收益写成结果。

## 2. 从前人工作，怎样走到这个 idea

把相关工作、剩余困难和思路推导写在同一条论证里。选最相关的两三条已有路线，从它们实际如何工作开始，逐步推出一个值得尝试的候选想法。读者应理解每次转折为什么发生。

在工作记录中先走通以下连接，再用连贯段落写出来：

1. **已有机制与能力。** 旧方法具体利用了什么信息、表示或反馈，因此已经能做到什么？介绍理解后续转折必需的机制，不能只列方法名和成绩。
2. **瓶颈及其原因。** 在哪种明确情形下，它依赖的条件不再成立，或优化目标无法鼓励想要的行为？用当时已有的失败观察或相关工作说明原因。仅说“泛化不足”“成本高”还不够。
3. **从瓶颈得到设计要求。** 要解除这个原因，必须补充哪类信息、改变哪个关系，或者放宽什么约束？解释为什么改动应当发生在这里，而非笼统地说需要更强的模型。
4. **已有知识如何满足要求。** 哪种已知机制恰好能提供所缺的信息或操作？具体解释它如何作用到上述瓶颈，以及迁移需要什么条件。两种技术分别有效，不足以证明组合有用。
5. **落到候选 idea。** 用一句话说清可以尝试怎样的改变、预期通过哪条路径带来收益。它应与本文核心思路相接，尚未验证的效果保留为假设；具体实现留到方法部分。

例如，“已有方法 A，也有技术 B，因此结合二者”省略了最重要的桥梁。应说明：A 的哪项限制恰好对应 B 提供的能力，B 需要的输入能否从 A 获得，接入后预计改变哪个结果。这里的设计要求必须由前面的瓶颈产生，不能先列出本文模块，再反向替每个模块寻找理由。

上述前提以本文最早公开日期为界，只采用此前已知的背景、失败模式、经验观察与工作。不能用本文新发现的现象、消融结果或后来成功证明“当时理应想到”。同期独立工作注明时间关系；后来的教程只能帮助今天解释术语。

这是基于历史证据的一种合理动机解释，不声称知道作者私下的思考过程。作者明确讲过的 inspiration 可直接引用。证据不足的连接简短交代，不虚构被作者放弃的路线，也不把本文设计说成唯一必然的答案。读完本节，读者应能自行复述从旧机制到新想法的因果连接。

## 3. 核心 intuition

用 2–4 句话收束上一节：论文改变了哪个关键关系，为什么预计会起作用，最重要的前提是什么。用读者已理解的概念讲本质，不再复述完整探索过程，也不用模块名称列表代替解释。

系统论文可以突出组件如何互相创造条件、共同解除瓶颈；不为追求一句漂亮口号虚构孤立的新算法。

## 4. 方法：先讲方法，再走一个简单例子

本节按“主要方法 → 简单例子”的顺序讲。前半回答论文具体做了什么，后半让读者看到这些步骤如何作用到一个输入。两遍有不同任务，例子不再重复通用定义。

### 先过一遍论文的主要方法

先用短段落给出输入、输出和整体步骤，再按论文的方法逻辑解释主要环节：每步接收什么、做什么、为什么需要、向下一步提供什么。覆盖支撑本文主张的核心设计和必要的配套环节，配套细节可一句带过；不要只挑一个熟悉模块讲解而漏掉整体方法。

训练与推理分别说清，必要时指出更新的参数、训练时可见的信息及部署时保留的组件。说明哪些机制沿用前人，本文究竟改动了哪里。只在理解机制需要时保留维度、参数或伪代码。代码与论文不一致时注明实际采用的版本，不能拼出不存在的实现。

**数学跟随对应的方法步骤。** 原文有决定理解的数学推导时，先解释该步要解决什么、用了什么假设，再引入符号与关键等式，说明非显然变换的依据，最后回到这一步实际计算什么。术语和前置知识补到读者能跟上推导即可；教学补步用自然措辞说明，不冒充作者的证明。

原文仅给出目标函数或定义时，可解释方法必需的符号与含义，不额外构造理论推导。没有相关数学推导时，直接讲机制与操作，不设数学空章节，不从教科书扩写一套推导来凑完整性。

### 再用一个简单例子走通

挑一个读者容易跟踪的输入，按前面的步骤展示关键中间变化和最终输出。优先使用论文或官方材料中容易理解的实例，给出来源；实际任务复杂时可以简化，或构造一个小的教学例子，首次引入时说明其性质。不要为坚持“真实”而让案例本身比方法还难懂。

例子必须具体到对象、输入和关键变化，不能只把方法再说一遍。没有运行时，只能引用公开结果或展示教学推演；不能编造真实中间日志、动作、数值或模型输出。对于理论论文，例子可以是一组满足假设的简单对象以及结论怎样应用，无需硬套预测流程。

## 5. 实验：问题、关键数据与结论

通常选 2–4 个最影响核心判断的问题，沿“想验证什么 → 如何对照或干预 → 数据是什么 → 得到什么结论”讲解。优先整体效果、关键设计的作用，以及会改变判断的边界或代价。

**直接呈现关键实验数据。** 从原文核实并整理成一张或少量紧凑表格，让读者不打开论文也能理解主要结果。表格以方法或实验设置为行、关键指标为列，或以干预条件为行；不要把整段实验描述塞进每个单元格。只选支撑上述问题的代表性结果和重要负结果，不复制所有排行榜。

- 表题或表注交代任务、数据集和协议；列名写清指标、单位及越高/越低越好的方向。必要时同时保留成功数与总次数、误差范围等原文信息。
- 区分不同任务、策略、数据量和预算；不把跨条件合计伪装成单一策略或同协议的对比。消融需交代实际改变的因素，控制不完全时按可支持的范围下结论。
- 原始数值、自行汇总和曲线估读分清。汇总须可复算，图中估值明确为近似；不可读或未报告的值不补造，也不捏造方差、种子数和显著性。
- 每张表后用一两句话解释最值得看的差异及其含义。来源链接放表注，原图表编号仅作为可选定位；不要以“见 Table 1 / Fig.4”代替数据或作为结论句。

原文没有量化实验时，按其定性证据或理论论证解释如何支持主张，不虚构数据表。若关键数据暂时无法取得，说明缺口，保留能核实的结果。

## 6. Take-aways

通常三条简短结论：应该更新什么认识、什么机制值得借鉴、在什么条件下适用。提炼读完论文后留下的判断，不复述算法步骤、完整摘要或全部数据，不引入新 claim。

## 7. 比较脆弱的假设

选 1–3 个与核心机制或主要结论最相关的依赖条件，按影响大小写。每项说清：方法依赖什么，为什么这个条件容易不成立或证据还弱，失效后会影响哪个环节和结论。无法证明哪项最脆弱时，不勉强排序为唯一的“最”。

具体到数据覆盖、反馈准确度、可观测信息、环境条件或其他实际机制。避免“数据量有限”“还需更多实验”这类无对象的限制。论文承认的限制直接引用，自行识别的风险保留适当的分析语气。一个简短失败情境有助于理解时可以使用。

本节只分析假设与适用边界，不要求一周计划、复现方案、资源预算、统计阈值或完整反例实验。不要因某个附属模块容易测试，就让它取代整篇论文的核心依赖。

## 8. Follow-up：一个值得继续想的方向

围绕尚未满足的需求与方法限制，简短提出一个有机制差异的候选。说清它准备改变什么、为什么可能绕过原有瓶颈，以及相对最接近工作还有什么值得验证的差异。优先新问题或关键机制，单纯加模块、换模型或扩大数据不能自动构成非增量研究。

按实际检索日期核查最接近的原始工作，查询日志留在工作记录，正文只保留决定新颖性判断的比较。一个可区分该想法与既有方案的预测即可，不扩写成完整实验计划。检索无法证明绝对原创；发现已有直接重合时修改候选或如实保留研究缺口，不硬凑“novel”。
