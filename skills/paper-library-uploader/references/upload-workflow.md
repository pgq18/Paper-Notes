# 上传与验证流程

本文件用于完成讨论整合后的远端上传及需要隔离验证的情形。发布对象是整合后的最终稿；初稿备份、讨论记录与会话导出不属于发布文件。以库中当前配置为准；下述路径描述 Paper Notes 现有结构，不替代实际检查。

## 1. 确定目标与改动范围

从 `git remote -v`、当前分支、跟踪分支、部署 workflow 和会话读取目标，不根据目录名拼接远端 URL。读取 `.github/workflows/deploy.yml` 与 `.vitepress/config.mts`；当前流程由 `main` 上的 push 或手动触发，先 build，再通过 deploy job 发布 GitHub Pages。功能分支上的提交本身不会触发这个 main 发布流程。

检查未提交、已暂存和未推送提交。确认将要推送的完整提交范围都属于本次授权；仅让新提交保持干净仍可能顺带发布之前的无关提交。存在无关工作时，在远端目标分支基础上建立必要的隔离检出或 `codex/` 分支，只带入本次成品与必要的已授权依赖。不要自动 stash、reset、丢弃或覆盖用户工作。

若新增主题分类等所需支持文件仅存在于用户未提交改动中，区分本次上传必需的最小依赖与无关改动。含义明确、完成本次上传必需的分类定义和相应生成结果可随上传授权一并带入；不要因此反复确认已清楚的范围。若无法分离无关变更或涉及额外功能发布，先完成隔离构建和候选 diff，再说明具体需要用户决定的范围；不能悄悄发布全部现场改动，也不能发布一个缺失分类定义的条目。

## 2. 验证候选

有锁文件时沿用仓库依赖安装方式，使用现有 Node 环境，不为笔记上传升级依赖。当前项目使用 `npm ci` 安装，`npm run docs:build` 已先运行 `npm run generate`；需要仅更新索引时使用 `npm run generate`。独立检查阶段生成的数据应在隔离副本中，不能提前把未获批笔记加入正式库。

共享生成文件可能含有其他未提交笔记的条目。此时在仅含本次授权内容和已发布基线的副本中重新生成，再核对候选 diff；不能因为文件名属于索引就连带提交其中的无关内容。

当前生成输出为 `index.md`、`papers/index.md`、`tags/index.md`、`.vitepress/generated/papers.mjs` 和 `.vitepress/generated/sidebar.mjs`。按实际 diff 提交发生变化的输出，不提交 `.vitepress/dist/`、`node_modules/`、`.tools/`、源 PDF 或临时抓取材料。若实际库已改为不跟踪生成文件，沿用其规则。

检查新笔记在生成索引中的路径和分类，核对本地附件、站内引用及外部来源 URL。当前配置 `ignoreDeadLinks: true`，因此构建成功仍需要单独检查新增链接。预览中抽查长公式与表格，确保 Markdown 中的标签未被当成 Vue 组件。仅修复本次引入的问题；既有故障无法安全修复时，报告阻碍而不把失败称为通过。

## 3. 提交与推送

只暂存明确属于本次上传的文件，使用具体路径和必要时的逐块暂存；不用 `git add .` 或 `git add -A`。再次检查 staged diff、非预期文件和即将推送的提交列表。

提交信息遵循 Conventional Commits，首行少于 72 个字符，例如 `docs(papers): add attention paper note` 或 `docs(research): add retrieval survey`。不添加 AI 署名；除非用户为具体人类明确要求，否则不添加 `Signed-off-by` 或 `Co-authored-by` footer。

在用户允许直接上传且目标分支允许时，沿现有流程普通推送，无需因个人偏好强制 PR。若分支保护或项目规范要求 PR，创建最小 PR，验证 CI；按工具能力将创建的 PR 附加到当前任务。PR 尚未合并时写清等待状态，不绕过分支保护、不自动取消检查、不声称已发布。只有已有授权明确涵盖合并时才执行符合项目规则的合并。

远端发生 non-fast-forward 时先 fetch 并检查新变化，在隔离检出中整合授权内容，重跑受影响验证；不要 force push、重置用户分支或覆盖他人修改。出现科学内容或用户批注的实质冲突时保留两边并请求取舍。

推送超时或响应不确定时，先读取远端目标分支，确认预期提交是否已到达；已到达则转入部署核实，未到达才在原因已明确后重试。认证、权限、网络或冲突持续阻碍时，留下成品、diff、验证结果和明确失败位置，不无限重试。

## 4. 核实发布

分开验证三个事实：目标提交已在远端、该提交对应的 workflow 已成功、线上目标页面包含本次内容。不要将 push 成功当成部署成功，也不要用旧 workflow 的成功替代本次结果。

根据实际部署输出的 `page_url`、GitHub Pages 设置、自定义域名和 `VITEPRESS_BASE` 确定站点根地址。当前 workflow 默认 base 为仓库名路径，可被仓库变量覆盖；站点开启 `cleanUrls`，页面路径须依据实际配置与生成路由组成。不得只用远端 owner/repo 猜一个 URL 就宣称页面在线。

查看对应提交的 Actions run、build/deploy job 及部署环境状态。成功后访问实际笔记页，核对标题和一段本次新增内容，确保看到的不是缓存旧页；验证至少一个索引入口。尚在运行、需要环境审批、失败或服务不可访问时如实报告其状态，提供可核查的 run/PR/提交链接。有限等待期间有状态变化再更新；达到当前可验证边界后交付 pending 状态，不擅自创建持续监控。

最终区分“本地已入库”“已提交未推送”“已推送等待部署”“PR 等待合并”和“页面已核实上线”。只有最后一种可直接表述为发布完成。
